# AGENTS.md — обязательные инструкции для всех ИИ-агентов

> Версия протокола: **1.0** · Последнее обновление: 2026-08-17
> Читается **первым** любым агентом (Claude Code, Codex, Cursor, Gemini CLI, Arena Agent, и т.д.)
> перед любым действием в этом репозитории.

---

## 0. TL;DR — цикл работы агента

```
1. git pull --rebase
2. Прочитать: AGENTS.md → .agent/STATUS.md → .agent/LOCKS.md → .agent/TASKS.md → .agent/HANDOFF.md
3. Взять задачу из .agent/TASKS.md → поставить лок в .agent/LOCKS.md → закоммитить лок СРАЗУ
4. Делать работу маленькими коммитами, пушить КАЖДЫЙ коммит немедленно
5. Обновить .agent/STATUS.md, .agent/CONTEXT.md, .agent/TASKS.md
6. Записать HANDOFF в .agent/HANDOFF.md (даже если задача не закончена!)
7. Снять лок, git push
```

**Золотое правило: никакая работа не считается сделанной, пока она не запушена в `main`.**
Локальные незапушенные изменения = потерянный контекст для следующего агента.

## 1. Идентификация агента

В начале сессии определи свой `AGENT_ID` в формате:

```
<модель-или-инструмент>-<машина>-<YYYYMMDD-HHMM>
пример: claude-code-mbp14-20260817-1420
пример: arena-agent-sandbox-20260817-1152
```

Используй его во всех записях STATUS/LOCKS/HANDOFF и в теле коммита (`Agent: <AGENT_ID>`).

## 2. Git-протокол (работа с разных машин, параллельно)

### 2.1 Базовые правила
- Ветка по умолчанию: `main`.
- **Всегда** `git pull --rebase` перед началом и перед каждым push.
- **Пушить сразу** после каждого логически завершённого шага. Не копить.
- Коммиты атомарные: один файл/одна мысль = один коммит, когда это возможно.

### 2.2 Формат коммита

```
<type>(<area>): <краткое описание>

<опционально: что изменилось и почему>

Agent: <AGENT_ID>
Task: <ID задачи из TASKS.md, например T-004>
```

`type`: `research` | `docs` | `feat` | `fix` | `chore` | `status` | `handoff`
`area`: `dispute` | `returns` | `legal` | `tooling` | `agent-protocol` | `sources` | ...

### 2.3 Конфликты
- Конфликт в `research/*` или `docs/*` → **объединять оба варианта**, ничего не удалять.
- Конфликт в `.agent/STATUS.md` → сохранить **обе** записи агентов, отсортировать по времени.
- Конфликт в `.agent/CONTEXT.md` → объединить, дубли пометить `<!-- DUP? -->`, не терять факты.
- Никогда не делать `git push --force` в `main`.

### 2.4 Длинные/рискованные работы
Если задача > ~30 минут или ломающая — работай в ветке `agent/<AGENT_ID>/<task-id>`
и пушь её тоже сразу, затем открой PR или мержи в `main` после проверки.

## 3. Параллельная работа: система локов

Файл `.agent/LOCKS.md` — единственный источник правды о том, что занято.

**Перед началом работы над файлом/областью:**
1. `git pull --rebase`
2. Проверить, нет ли активного лока на эту область.
3. Добавить строку лока, закоммитить и **запушить немедленно** (коммит `chore(agent-protocol): lock ...`).
4. Если push отклонён — значит другой агент успел раньше: перечитать локи и выбрать другую задачу.

**Правила локов:**
- Лок живёт максимум **90 минут**. Просроченный лок любой агент вправе снять
  (записав в `.agent/HANDOFF.md` факт снятия и причину).
- Один агент = максимум 2 активных лока.
- Снятие лока — отдельный коммит сразу после завершения работы.

**Формат строки лока:** см. шапку `.agent/LOCKS.md`.

## 4. Сохранение статуса и контекста (главное требование проекта)

Каждый агент **обязан** оставить после себя воспроизводимый контекст.

### 4.1 `.agent/STATUS.md`
Обновляется **в начале** сессии (запись «в работе») и **в конце** (запись «завершено/прервано»).
Всегда содержит: кто, когда, что делал, где остановился, что дальше.

### 4.2 `.agent/HANDOFF.md`
Запись добавляется **в конце любой сессии** — даже если работа не завершена или
завершена аварийно (лимит контекста, ошибка, прерывание пользователем).
Минимальный набор полей — шаблон в самом файле.

### 4.3 `.agent/CONTEXT.md`
Сюда попадают **выводы, а не процесс**: проверенные факты, найденные закономерности,
тупики («это уже пробовали, не работает»), ключевые источники.
Цель: следующий агент не должен повторять исследование заново.

### 4.4 `.agent/DECISIONS.md`
Любое решение, влияющее на структуру, границы или методологию проекта, — как ADR-запись.

**Ни один коммит с содержательной работой не должен уходить без обновления STATUS + CONTEXT.**

## 5. Стандарты исследовательской работы

1. **Каждый факт — с источником.** Формат сноски: `[источник](URL) — дата обращения`.
2. **Датируй знания.** Правила AliExpress меняются; помечай `Актуально на: YYYY-MM-DD`.
3. **Разделяй уровни достоверности:**
   - `[ОФИЦИАЛЬНО]` — правила/справка AliExpress, законы.
   - `[СООБЩЕСТВО]` — Reddit/форумы/Telegram: массовый опыт, но не гарантия.
   - `[ЕДИНИЧНО]` — один отзыв, требует подтверждения.
   - `[ГИПОТЕЗА]` — вывод агента, не подтверждён.
4. **Никогда не выдумывай URL, номера правил, суммы и сроки.** Не уверен — помечай `[TODO: проверить]`.
5. Противоречия между источниками фиксируй явно, а не «сглаживай».
6. Все новые материалы регистрируй в `research/00-INDEX.md`.

## 6. Границы проекта (обязательно к соблюдению)

Полный текст — `docs/SCOPE_AND_ETHICS.md`. Кратко:

**МОЖНО и НУЖНО:**
- Разбирать официальные правила Buyer Protection, сроки, категории споров.
- Строить методики выбора товаров/продавцов с минимальным риском и максимальной защитой
  (Free Return, Choice, локальные склады, история магазина).
- Составлять законные плейбуки для реальных проблем: не пришло, брак, не то, повреждено.
- Анализировать теневую «рефанд-индустрию» **как явление**: экономика, роли, каналы,
  почему платформа это ловит, какие последствия — с позиции threat intelligence / анти-фрода.
- Разрабатывать инструменты учёта: дедлайны споров, трекинг заказов, скоринг риска продавца.

**НЕЛЬЗЯ:**
- Пошаговые инструкции по получению возврата за товар, с которым всё в порядке.
- Шаблоны ложных заявлений, поддельных доказательств, «текстов для спора» под ложные причины.
- Списки/парсеры «скрытых товаров» и «магазинов-однодневок» для гарантированного рефанда.
- Автоматизация массовых споров, мультиаккаунтинг, обход антифрода, работа с чужими аккаунтами.
- Любая помощь реф-сервисам, торгующим «рефанд-услугами».

Если задача из `TASKS.md` пересекает границу — агент **обязан** отказаться,
пометить задачу `BLOCKED-SCOPE` и записать причину в `.agent/DECISIONS.md`.

## 7. Технические конвенции

- Язык документов: **русский** (термины и цитаты источников — в оригинале).
- Markdown, строки желательно ≤ 120 символов, заголовки по иерархии.
- Имена файлов: `NN-kebab-case.md` в `research/`.
- Код: Python 3.11+, стандартная библиотека по умолчанию; зависимости — только с обоснованием в PR/ADR.
- Никаких секретов в репозитории: токенов, паролей, cookie, персональных данных.
  Если нашёл секрет в истории — записать в `.agent/STATUS.md` как инцидент и уведомить владельца.
- Никаких реальных номеров заказов/адресов в примерах — только вымышленные.

## 9. Что делать, если ты «упал» на середине

Пиши HANDOFF **до** того, как закончится контекст:
как только видишь, что задача большая, сразу зафиксируй промежуточный HANDOFF и запушь.
Лучше три коротких handoff-записи, чем одна ненаписанная.
